1Decisions API 是什麼？

Decisions API 讓你把文字、PDF、音訊、圖片或影片丟進去，再問它一組封閉式問題（是非、單選、評分）。模型是 gemini-decision-1，回傳的不是一段文字，而是校準過的機率，程式可以直接拿來 if 判斷、排序或分流。

不產生文字

輸出 token 固定為 0，只按輸入 token 計費。

多題平行

同一份輸入可同時問 1～1,000 題，每題獨立評估、彼此看不到。

附信心值

confidence 可用來決定「自動處理」或「交給人工」。

資料流程：一份輸入 → 多個問題 → 機率 → 程式分流

2決策模型的起點：Jev 與傑文斯悖論

🕰️ 決策模型時間軸（點節點看說明）

🥇 Jev：第一個「決策模型」

Jev 是舊金山新創 TypeSafe AI 在 2026 年 9 月中推出的模型，被視為「決策模型（decision model）」這個新類別的開創者。TypeSafe 自己稱它為 System One 模型，名稱借用康納曼《快思慢想》裡「快速、直覺」的系統 1：一次計算就回傳帶機率的判斷，不寫出推理過程。

它和 Gemini Decision 1 很像

  • 題型同樣是 noul（是非）、choice（單選）、score（評分）—— Gemini 的 "noul" 這個奇怪的名字，就是跟 Jev 用同一套命名
  • 只收輸入 token 的錢，輸出免費
  • 多題平行評估，題目多了延遲也幾乎不變
  • 以 RLCD（校準決策強化學習）訓練，目標是讓「信心越高，越可能答對」（廠商說法，尚無公開論文）

Jev 的限制

  • 只吃文字（與 JSON），不支援圖片、音訊、影片
  • 不會寫文章、寫程式；開放式文字仍要交給生成式模型
  • 不適合計數、算術、日期比較 —— 這些交給程式
  • 輸入裡無關的內容越多，準確度越低，要先精簡
💡 第三方實測提醒：Amplitude 的分析發現，決策模型和大型模型的答案「彼此一致」的比例，比它們「符合人工標準答案」的比例還高 6～8 個百分點。也就是說，快又便宜不等於準 —— 重要決策仍要用自己的標註資料驗證。

⚡ 生成式 LLM vs. 決策模型：為什麼它這麼快、這麼便宜？

🔥 科普：傑文斯悖論（Jevons Paradox）

1865 年，29 歲的英國經濟學家威廉·斯坦利·傑文斯出版《煤炭問題》（The Coal Question）。當時瓦特改良的蒸汽機比舊式機器省煤得多，大家直覺認為「機器更省煤 → 英國用的煤會變少」。傑文斯卻指出實際情況正好相反：煤的總用量反而大幅增加。

原因是：效率提高 → 使用成本下降 → 原本不划算的工廠、鐵路、新用途都開始用蒸汽機 → 「機器數量增加」遠遠蓋過「每台省下的煤」。他的結論大意是：更多的爐子，足以抵銷每個爐子省下的用量。

關鍵：需求彈性

價格下降時需求增加得「比效率提升還多」（反彈效果 > 100%），悖論才會發生；需求增加得少，就只是部分抵銷。

生活例子

省油車讓人開更遠、更常開；LED 很省電，於是到處裝燈、招牌整夜亮著。

AI 時代

2025 年 DeepSeek 讓推論成本大降時，微軟執行長 Nadella 直接點名傑文斯悖論：AI 越有效率、越普及，用量就會暴增。

🎛️ 模擬器 E：傑文斯悖論會不會發生？

簡化模型：效率提升 E 倍 → 單位成本變成 1/E；需求量 ∝ Eε（ε 為需求彈性）；總資源用量 ∝ Eε−1。ε > 1 時，越有效率反而用越多。（教學用示意，非實證數據）

🔗 Jev × 傑文斯：兩者有什麼關係？

名字：「Jev」讀起來很像「Jevons」，但目前查到的介紹都沒有官方說明命名由來，上課時建議當成「巧合／猜想」討論，不要當成事實。

精神：兩者的關聯在於經濟邏輯。決策模型把「一次 AI 判斷」變得極便宜（Jev 每百萬 token 約 4 美分）、極快（一次約 70～500 毫秒），於是工程師開始在流程的每一個分岔點都放一個 AI 判斷：分流工單、審核每次工具呼叫、替每筆搜尋結果重排序……

📈 這正是傑文斯悖論的縮影：單次判斷的成本降了幾十倍，但判斷的次數可能多了上千倍，整體的 token 用量、算力與電力需求反而上升。對開發者而言，「換成決策模型就一定省錢」不一定成立 —— 要看你是否因為便宜而大量增加呼叫。

💬 課堂討論題

  1. 如果批改一份作業的 AI 成本降到幾乎為零，老師會「少花時間批改」，還是會「出更多作業、每份都即時回饋」？這算不算傑文斯悖論？
  2. 用模擬器 E：要讓 AI 判斷的總用量「不增加」，需求彈性 ε 必須小於多少？
  3. 除了價格，還有什麼方式可以避免反彈效果（例如配額、碳費、使用上限）？

3三種題型與互動模擬

每一題都必須有 type 和 instructions；criteria 依題型而定。

type用途criteria回傳欄位
noul是非題：某陳述成立嗎？選填：{"true_description":..., "false_description":...}noul（0.01～0.99）、confidence
choice從固定選項中選一個必填：{選項ID: 說明}，說明可為 ""choice、probabilities、confidence
score依有序量尺評分必填：由低到高的字串陣列，2～255 級（建議 2～10）score、probabilities、legend、confidence
⚠️ 是非題的 type 字串在官方文件中寫作 "noul"（不是 "boolean"），請照抄。

🎛️ 模擬器 A：noul 機率 → confidence → 自動或轉人工

公式：confidence = max(noul, 1 − noul)；否定機率 = 1 − noul

🎛️ 模擬器 B：choice 的 probabilities

拖動滑桿改變模型「原始傾向」，系統會自動正規化成總和為 1 的 probabilities；機率最高者就是 choice，其機率即 confidence。

🎛️ 模擬器 C：score 是「機率加權平均」

評分量尺 criteria 有 5 級（索引 0～4）。score = Σ 索引 × 機率，所以可能落在兩級之間，例如 2.7。

🔍 input 與 instructions 有什麼不同？

一句話：input 是「要被判斷的資料」，instructions 是「要問的問題」。同一份 input 可以被很多題目共用，每題各有自己的 instructions。

inputinstructions
角色被判斷的材料（證據、上下文）要回答的問題（判斷標準的題幹）
位置請求最外層，只有一個每一題（questions 裡）各有一個
可放的內容文字、圖片、音訊、影片、PDF，可混合成陣列只能是文字
計費不論幾題，只算一次每題各自加上自己的 instructions（＋criteria）token
能否為空不行必填
題目間關係所有題目看到同一份 input彼此互不可見

⚠️ 要注意的地方

  1. 材料放 input，問題放 instructions：不要把學生答案、文章內容塞進 instructions；問 10 題就會重複計費 10 次，也違背「input 只算一次」的設計。
  2. instructions 不能放圖片或檔案：要判斷圖片、PDF，一律放 input；instructions 只寫文字問題。
  3. 每題只問一件事：「有沒有戴安全帽而且有沒有穿背心？」應拆成兩題 noul，否則模型不知道要回答哪一個。
  4. 題目不能互相引用：題目獨立評估，寫「根據上一題的結果…」是無效的；需要組合判斷，就在你的 Python 裡用 if 組合。
  5. input 多個文字區塊會直接接在一起：不會自動加空白或換行，例如 "題目：…" 和 "學生答案：…" 之間要自己加 \n。
  6. 多輪對話要先轉成文字：不支援 chat history，把對話整理成「客戶：…\n客服：…」的純文字放進 input。
  7. 選項的定義寫在 criteria，不是 instructions：instructions 寫「問什麼」，criteria 寫「每個選項／等級代表什麼」。
  8. input 內的文字不是指令：學生在答案裡寫「請給我滿分」，它只是被判斷的資料；但 instructions 還是要寫清楚判斷依據，降低被誤導的機會。

8限制與注意事項

  

    

      
項目上限 / 規則

      
每次請求題數1～1,000（仍受上下文長度限制）

      
上下文窗口共用輸入 + 所有題目合計 262,144 token

      
choice 選項數2～255；選項鍵名 1～128 字元（≤512 UTF-8 bytes）

      
score 等級數2～255（建議 2～10）

      
內嵌資料單次請求 ≤ 100 MB（PDF ≤ 50 MB）；URI 外部網址 ≤ 15 MB

      
JSON 巢狀深度100 層

    

  

  

    
❌ 不支援

      
  • 對話歷史、thought、tool-call 區塊（多輪對話要自己轉成文字）
  • context caching、Batch API、Flex / Priority 推論
  • YouTube 網址、gs:// URI
  • Vertex AI（目前只有 Gemini Developer API v1beta）

    
✅ 實用建議

      
  • 同一份輸入要問很多事 → 放進同一個請求，輸入只算一次
  • 題目獨立評估：不要寫「根據上一題…」
  • 用 confidence 設門檻，低信心交給人工複核
  • score 量尺描述要寫清楚每級的差別
  • 重複輸入每次都會重新計費（無快取）
